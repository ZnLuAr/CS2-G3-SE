# 代码审计

这个 skill 在代码提交或 PR 前执行**全面且准确**的审计，确保改动符合项目规范、业务逻辑正确且不引入安全或质量问题。

**审计原则**：
- **不追求速度，追求准确**：逐个文件、逐个函数仔细检查
- **使用 sub-agent**：大改动（10+ 文件）或跨多个模块时，派遣多个 sub-agent 并行审计，确保不遗漏
- **双向检查**：既要检查代码本身的问题，也要检查文档是否同步
- **安全问题需要具体路径**：说明可触发的输入、经过的代码和造成的影响，避免用缺少企业级设施作为问题依据
- **优先最小修复**：在现有接口、分层和课程项目范围内修复明确风险；只有现有契约无法正确表达行为时才建议改接口

**本项目的基础安全范围**：

- 外部输入检查类型、长度、格式和范围
- SQL 值使用参数绑定，动态标识符使用固定白名单
- 密码使用成熟库哈希，不进入普通输出和日志
- 权限在服务层校验，停用账号重新验证
- 错误和日志隐藏密码、连接串、完整联系方式与体测明细

明确标注且尚未进入本轮交付范围的 `NotImplementedError` 视为占位状态。已实现入口依赖该占位方法而无法完成本轮承诺流程时，报告为集成阻塞项，并指出应由哪个依赖交付解决。

**审计范围**：业务服务层（services）、数据访问层（repositories）、数据模型（models）、CLI 界面。

**测试统一后续进行**：本项目测试在后续统一编写，代码审计不包含测试维度。

---

##  审计策略

**全面且精确**：不按改动类型选择性审计，而是对所有维度进行全面检查。

**使用 sub-agent 并行审计**：
- **文档比对 agent**（1-2 个）：检查改动是否同步到文档
- **代码审计 agent**（若干个）：按文件或模块分配，每个 agent 负责：
  - 业务逻辑审计
  - 安全性审计
  - 代码质量审计
  - 设计优雅度审计
  - 性能审计

**审计流程**：
1. 分析改动范围，识别所有受影响的文件
2. 为每个文件或模块启动一个代码审计 agent
3. 启动文档比对 agent，检查文档同步
4. 汇总所有 agent 的发现，并提出可行的修改建议，生成完整报告

##  审计流程

### 0 准备：摸清改动范围并分配 sub-agent

首先列出所有改动文件，按模块职责归类，然后分配 sub-agent 并行审计。

**执行命令：**
```bash
git status --short
git diff --stat
```

**分析要点：**
- 改动涉及哪些模块？（services / db / models / ui / docs）
- 改动涉及哪些负责人的任务？（参考 [architecture.md](../../../docs/architecture.md) #你要实现哪个模块）
- 有多少个文件？每个文件的改动规模如何？

**分配 sub-agent 策略：**

1. **代码审计 agent**（按文件或模块分配）：
   - 每个文件或模块启动一个 agent
   - 每个 agent 执行完整的审计维度（业务逻辑、安全性、代码质量、设计优雅度、性能）
   - 示例：
     - Agent 1: 审计 `src/services/member_service.py`
     - Agent 2: 审计 `src/services/product_service.py`
     - Agent 3: 审计 `src/db/repositories/member_repo.py`

2. **文档比对 agent**（1-2 个）：
   - Agent A: 检查 `docs/architecture.md` 是否同步改动
   - Agent B: 检查 `README.md` 和其他文档是否需要更新

**sub-agent 模板**：
```
/agent "审计 <文件路径>：
1. 业务逻辑：返回类型、异常使用、事务管理、业务规则
2. 安全性：输入验证、SQL 注入、密码处理、权限检查
3. 代码质量：命名、职责、复杂度、错误处理
4. 设计优雅度：抽象、继承、复杂度、职责划分
5. 性能：N+1 查询、索引、分页、缓存

请逐项检查，记录所有发现的问题。"
```

### 1 业务逻辑审计

**检查清单：**

- [ ] **返回类型规范（核心规则）**
  - 查询单条记录：找到返回 View 对象，找不到抛 `NotFoundError`，**禁止返回 None**
  - 查询列表：有结果返回 `Page(items=[...], total=N)`，无结果返回 `Page(items=[], total=0)`，**禁止返回 None 或裸列表**
  - 修改记录：成功返回修改后的 View 对象，失败抛异常，**禁止返回 True/False**
  ```bash
  # 检查是否有违规返回 None
  git diff | grep -n "return None" | grep -v "# "
  
  # 检查是否有返回布尔值的业务方法
  git diff | grep -n "return True\|return False" | grep -v "# " | grep -v "def _"
  ```

- [ ] **异常使用正确性**
  - 输入不合法 → `InvalidInputError`（姓名为空、金额为负）
  - 没有权限 → `PermissionDenied`（会员查询别人档案）
  - 账号失效 → `AuthenticationError`（账号被停用）
  - 记录不存在 → `NotFoundError`（查询不存在的编号）
  - 业务冲突 → `ConflictError`（重复预约同一课次）
  - 状态不允许 → `InvalidState`（已取消的预约不能签到）
  - 数据库失败 → `StorageError`（数据库连接断开）
  
  检查改动中的异常类型是否选对，不要用通用 `Exception` 或 `ValueError`。

- [ ] **事务管理规范**
  - 在**业务服务层**（`*_service.py`）提交或回滚事务
  - **数据访问层**（`*_repo.py`）**禁止**提交事务
  ```bash
  # 检查 repo 文件是否违规提交
  git diff src/db/*.py | grep -n "session.commit()\|session.rollback()"
  ```
  
  - 一个业务操作涉及多个表时，必须在同一个事务中完成
  - 使用 `with session.begin():` 管理事务边界

- [ ] **字段类型正确性**
  - ID 和编号：`int` 或 `str`（UUID）
  - 金额：`Decimal`，**必须用字符串构造**：`Decimal("199.00")`
  - 日期时间：`date`（纯日期）、`datetime`（带时区时刻，内部转 UTC）
  - 状态值：`Literal["active", "void"]`（固定英文值）
  - 可空字段：`str | None`（用 `None` 表示空，不用空字符串）
  ```bash
  # 检查是否有 float 类型的金额
  git diff | grep -n "float" | grep -i "price\|amount\|balance"
  
  # 检查 Decimal 是否用字符串构造
  git diff | grep -n "Decimal(" | grep -v 'Decimal("'
  ```

- [ ] **并发控制与锁顺序**
  - 涉及并发操作时，是否使用了行锁（`FOR UPDATE`）？
  - 多资源加锁时，是否按固定顺序（通常按 ID 排序）避免死锁？
  - 在锁内是否重新读取最新数据，而非使用锁外读取的旧数据？
  
  **典型场景**：
  - 销售产品：锁定会员 → 锁定产品 → 读取最新到期日
  - 预约课次：锁定会员 → 锁定课次 → 锁定产品 → 读取最新容量和余额
  - 取消课次：收集预约列表 → 按会员 ID 排序 → 逐个锁定处理

- [ ] **业务规则完整性**
  参考 [architecture.md](../../../docs/architecture.md) 中的业务规则章节，检查：
  
  **产品规则**：
  - 私教课产品续购是否正确接续（查询最晚到期日）
  - 次卡是否从今天生效（不参与接续）
  - 课节初始化是否正确（remaining = 赠课数，reserved = 0）
  
  **门禁规则**：
  - 同一会员同一天是否去重（按 member_id + business_date 唯一）
  - 私教课产品入场是否不扣次（accesses_used = 0）
  - 次卡入场是否扣次（accesses_used = 1）
  
  **预约规则**：
  - 次卡是否禁止预约私教课
  - 产品日期资格检查是否正确（valid_from <= 上课日期 < valid_until）
  - 课节余额计算是否正确（available = remaining - reserved）
  - 时间冲突检查是否使用前含后不含区间（[start, end)）
  - 重复预约检查是否包括所有状态（含已取消）
  
  **签到与消课规则**：
  - 签到是否检查开课时间（必须从开课时间起）
  - 消课是否检查已签到状态
  - 缺席是否只释放占用不扣课节（reserved -= 1, remaining 不变）
  - 预约状态流转是否正确（reserved → checked_in → completed）

- [ ] **权限检查完整性**
  - 每个业务方法开头是否调用 `auth.verify_actor()`？
  - 权限判断是否符合角色定义？
    - 会员：只能操作自己的数据
    - 教练：只能操作自己的课次和有权限的会员
    - 前台：可以代办会员业务
    - 管理员：全部权限
  - 会员查询别人的数据是否返回 `NotFoundError`（不暴露是否存在）？

- [ ] **防重复提交机制**
  - 关键操作（销售产品、预约、入场）是否使用 `request_id`？
  - 相同 request_id + 相同输入是否返回原结果（幂等）？
  - 相同 request_id + 不同输入是否抛 `ConflictError`？
  - 提交结果未知时，是否抛出 `OutcomeUnknownError` 并携带 request_id？

### 2 安全性审计

本节按上面的基础安全范围检查。每条发现必须包含实际触发方式和影响；修复方案优先复用现有异常、校验、权限和日志接口。

**检查清单：**

- [ ] **输入验证**
  - 用户输入是否经过验证（长度、格式、范围）？
  - 数值输入是否检查边界（金额非负、评分 1-5、体测数值范围）？
  - 字符串输入是否去除首尾空白、检查长度？
  ```bash
  # 检查是否直接使用用户输入而未验证
  git diff | grep -n "input\|data\[" | grep -v "validate\|check\|strip\|len("
  ```

- [ ] **SQL 注入防护**
  - 是否使用参数化查询（占位符 `?` 或 `:param`）？
  - **禁止**字符串拼接 SQL
  ```bash
  # 检查是否有 SQL 字符串拼接
  git diff | grep -n 'f".*SELECT\|f".*INSERT\|f".*UPDATE\|f".*DELETE'
  ```

- [ ] **密码处理**
  - 密码是否使用哈希算法加密存储（如 bcrypt、scrypt）？
  - 密码是否原样存储（不转小写、不去空白）？
  - 日志中是否避免记录密码明文？
  ```bash
  # 检查是否有密码明文记录
  git diff | grep -n "password" | grep -i "log\|print"
  ```

- [ ] **敏感数据脱敏**
  - 日志中是否脱敏处理敏感信息（密码、体测明细、完整联系方式）？
  - 错误消息是否避免暴露内部信息（SQL、连接字符串）？
  - 体测数据查看是否按权限规则过滤（基于预约授权截止时刻）？

- [ ] **权限绕过风险**
  - 是否可能通过构造特殊输入绕过权限检查？
  - 批量操作是否对每条记录都检查权限？
  - 账号被停用后，现有 Actor 是否能继续操作？

### 3 代码质量审计

**检查清单：**

- [ ] **命名规范**
  - 类名：PascalCase（`MemberService`、`AuthService`）
  - 函数/方法/变量：snake_case（`get_member`、`create_account`）
  - 常量：UPPER_SNAKE（`MAX_SESSIONS`、`DEFAULT_TIMEOUT`）
  - 私有成员：前导下划线（`_validate_input`）
  - 文件名：snake_case（`member_service.py`、`auth_repo.py`）
  
  根据项目实际约定检查命名风格是否一致。

- [ ] **函数职责单一性**
  - 函数是否只做一件事？
  - 是否存在"又查询又修改又发送消息"的多职责函数？
  - 建议拆分：查询逻辑、业务逻辑、数据持久化分别独立

- [ ] **复杂度控制**
  - 是否存在过深嵌套（连续 3+ 层 if/for/try）？
  - 能否用 early return / continue 摊平控制流？
  - 是否存在明显重复代码？可提取公共函数？

- [ ] **错误处理完整性**
  - 是否捕获了所有可能的异常路径？
  - 是否存在裸 `except:`、吞异常、静默失败（`except: pass`）？
  - 错误日志是否保留足够上下文（操作人、记录编号、操作类型）？
  - 是否使用了项目统一的错误处理机制（`handle_error`）？

- [ ] **边界情况处理**
  - 是否考虑 `None`、空字符串、空列表等边界输入？
  - 是否考虑重复调用、重复初始化（幂等性）？
  - 时间边界是否正确（恰好到期、恰好开课、跨午夜）？

- [ ] **代码清洁度**
  - 是否存在未使用的变量、函数、import？
  - 是否存在不可达代码（return 之后、永假分支）？
  - 是否遗留 `print` / `TODO` / `FIXME` / 注释掉的代码？
  ```bash
  # 检查调试残留
  git diff | grep -nE "(^\+.*\bprint\()|TODO|FIXME|XXX|# .{50,}"
  ```

- [ ] **类型注解完整性**
  - 函数签名是否有类型注解（参数、返回值）？
  - 复杂类型是否使用了 `typing` 模块（`List`、`Dict`、`Optional`、`Literal`）？
  - 是否与实际代码行为一致？

- [ ] **文档字符串**
  - 公共函数/类是否有 docstring？
  - docstring 是否说明参数、返回值、异常？
  - 是否提供业务场景示例？

### 4 设计优雅度审计

> **这个维度找的不是错误，是「正确但做复杂了」或「设计不够优雅」。**
> 角色设定：一个有经验的架构师审查代码，关注的是「这段代码能工作，但设计上有问题」。

**与 3 的区别**：3 检查的是客观对错（命名错误、职责混乱、边界遗漏），本维度处理的是设计层面的问题——抽象是否恰当、继承是否合理、复杂度是否必要。

**仅对新增功能 / 重构执行**；bug 修复、文档改动跳过（bug 修复以最小 diff 为美，这里挑刺会催生不必要重构）。

#### 检查清单

- [ ] **抽象是否恰当**
  - 每个新增的 class / wrapper / manager / service，问一句：**它消除了什么复杂度？**
  - 答不出来就是为分层而分层，**过度抽象与抽象不足同罪**
  - 反向检查：多处代码在表达同一个概念（同样的"查询→验证→处理→记录"骨架），即使字面不同也该收敛
  
  **过度抽象的信号**：
  - 只有一个实现的抽象类/接口
  - 只是简单转发调用的包装层（`WrapperService.do_something()` 只是调用 `RealService.do_something()`）
  - 泛型/参数过于灵活但实际只用一种方式
  
  **抽象不足的信号**：
  - 多处重复相同的业务流程骨架（不是代码重复，是概念重复）
  - "查询会员→验证权限→检查产品→锁定资源→执行操作→记录日志"这种流程在多个 service 中重复出现

- [ ] **继承层次是否合理**
  - 继承深度是否超过 2 层（基类→子类→孙类已是警戒线）？
  - 子类是否真的是 "is-a" 关系，还是只想复用代码？
  - 是否应该用组合（has-a）而非继承？
  
  **继承滥用的信号**：
  - 子类需要覆盖父类大部分方法
  - 子类和父类的职责完全不同（只是碰巧有些相似代码）
  - 为了复用几个工具方法而建立继承关系
  
  **正确做法**：
  - Python 优先用组合和协议（Protocol），少用继承
  - 工具方法提取到独立的 helper 模块
  - 业务模式用 Repository / Service 分层而非继承

- [ ] **有没有明显更简单的实现**
  - 这是整个维度的核心问题
  - 实现比问题本身复杂时，通常是把某个前提想难了
  - 主动构造一个「更简单或更自然」的写法，比较：
    - 复杂度（代码量 + 认知步骤）
    - 耦合（改 A 会不会牵动 B）
    - 变化传播（下一个需求来时会扩散到几处）

- [ ] **是不是不必要的防御**
  - 对类型系统/调用方契约已保证的前提再加检查（如 `if is None` / `hasattr`），是把不变量当变量处理
  - 删掉更稳（少一条永假分支）
  
  **例子**：
  ```python
  # 阻塞项 不必要的防御
  def get_member(self, actor: Actor, member_id: int) -> MemberView:
      if actor is None:  # Actor 类型注解已保证非空
          raise ValueError("actor 不能为空")
      if not isinstance(member_id, int):  # 类型注解已保证
          raise TypeError("member_id 必须是整数")
      ...
  
  # 通过项 信任类型系统
  def get_member(self, actor: Actor, member_id: int) -> MemberView:
      # 直接使用，类型系统已保证
      ...
  ```

- [ ] **命名说没说清语义**
  - `data` / `result` / `info` / `temp` / `obj` 合规但不达意
  - 变量名应该回答「这是什么」而非「这有个东西」
  - 函数名应该是动词开头（`get_member` / `validate_input`）
  - 布尔变量应该是 `is_` / `has_` / `can_` 开头（`is_active` / `has_permission`）

- [ ] **正常路径读得出来吗**
  - 摊平嵌套之后，主线有没有被异常分支淹没？
  - 读者能否从上往下读出「验证、验证、验证、业务」的结构？
  - 核心业务逻辑是否被埋在深层 if/try 中？
  
  **改进方向**：
  - 用 early return 处理异常分支
  - 验证逻辑提取到独立函数
  - 主流程保持在顶层缩进

- [ ] **状态的所有权清楚吗**
  - 每个新增的可变状态（全局变量、类属性、缓存）：
    - 谁创建、谁修改、谁清理？
    - 何时失效？
    - 并发下会不会双写？
  - 说不清楚就是味道

- [ ] **职责划分是否清晰**
  - Service 层：业务逻辑、权限校验、事务管理
  - Repository 层：数据库操作、查询构造
  - Model 层：数据结构定义、字段验证
  
  **越界的信号**：
  - Repository 中有业务判断（如检查余额、计算到期日）
  - Service 中拼接 SQL 或直接操作 ORM 细节
  - Model 中有数据库查询或业务逻辑
  
- [ ] **变化传播分析**
  - 主动假想 2-3 个可预期的需求变化：
    - 字段类型变（如 member_id 从 int 改为 UUID）
    - 数据源变（如产品配置从代码改为数据库）
    - 同一逻辑多一个入口（如预约除了 CLI 还要支持 API）
  - 问：变化会扩散到几处？
  - 扩散面大的，说明切分线画错了位置

#### 报告格式（每条发现五要素，缺一不算）

```markdown
### 设计优雅度 设计优雅度发现

- **位置**：`services/booking_service.py` 的 `book()` 方法（行 150-220）
- **问题机制**：在一个 70 行的函数中同时承担"解析输入、权限检查、产品验证、课次验证、
  容量检查、时间冲突检查、余额检查、创建预约、记录日志"九个职责。虽然逻辑正确，但认知负担重。
- **替代实现**：拆分为：
  - `_validate_booking_input()` — 验证输入和权限
  - `_check_booking_eligibility()` — 检查产品、课次、容量、时间、余额（返回验证结果对象）
  - `_create_booking_record()` — 创建预约和记录日志
  主流程变为 3 步调用，每步职责单一。
- **为什么更好**：下次改验证规则时只动一个函数；认知成本从"通读 70 行理清九种关注点"
  降为"各读 20 行"；测试可以针对各子步骤独立进行。
- **值得现在改吗**：如果本次 diff 触及该函数，顺手改成本低；否则记 TODO 而非阻塞。
```

#### 静默规则（什么时候必须闭嘴）

以下情况一律不报：

- **收益不够大** — 节省 < 10 行且不降低耦合的，不值得打断
- **与项目既有模式一致** — 局部更优但全项目都这样（如都传 dict、都用某种命名），改了反而破坏一致性
- **两种写法都站得住** — 剩下的只是偏好差异，报出来是噪音

#### 报告纪律

这一维度的产出可以是「无发现」— 对 1-3 个文件的小改动，无发现是正常结果。**禁止为了显得审过而降格报告凑数。**

### 5 性能审计

**检查清单：**

- [ ] **N+1 查询问题**
  - 是否在循环中执行数据库查询/网络请求？
  - 能否批量查询后在内存中关联？
  ```bash
  # 检查循环中的查询
  git diff | grep -A 10 "for .* in" | grep "query\|select\|get_"
  ```

- [ ] **索引使用**
  - WHERE 子句中的字段是否有索引？
  - JOIN 的关联字段是否有索引？
  - 频繁查询的字段组合是否考虑复合索引？

- [ ] **分页与限制**
  - 列表查询是否强制分页（禁止一次返回所有记录）？
  - 是否设置合理的默认页大小和最大页大小？
  - 导出功能是否分批读取而非一次加载全部？

- [ ] **缓存使用**
  - 频繁访问的不变数据是否缓存（产品列表、教练列表）？
  - 缓存是否有失效机制（数据更新时清除）？
  - 是否避免缓存穿透（查询不存在的数据）？

- [ ] **资源释放**
  - 数据库连接是否及时关闭（使用 `with` 语句）？
  - 文件句柄是否正确释放？
  - 长时间占用的锁是否及时释放？

### 审计优先级

**必查（阻塞提交）：**
1. 业务逻辑：返回类型规范、异常使用、事务管理
2. 安全性：密码处理、SQL 注入、权限检查

**重点查（易遗漏）：**
3. 并发控制：锁顺序、锁内重读
4. 业务规则：产品接续、门禁去重、预约资格
5. 文档同步：architecture.md、README.md

**细节查（影响代码质量）：**
6. 代码质量：命名、职责、复杂度、错误处理
7. 性能：N+1 查询、索引、分页
8. 边界情况：None、空值、时间边界

**判断查（仅新增功能/重构，不阻塞）：**
9. 设计优雅度：抽象是否恰当、继承是否合理、有没有更简单实现

##  使用建议

- **小改动（1-3 个文件）**：单线程逐项检查，15-20 分钟完成
- **中改动（4-10 个文件）**：重点查业务逻辑、安全性、文档和设计优雅度，其他项快速过
- **大改动（10+ 个文件 / 跨模块）**：强烈建议派 sub-agent 并行审计不同维度

**记住：代码审计不是附加流程，而是保证代码质量的最后一道防线。宁可多花 20 分钟审计，也不要事后返工。**
