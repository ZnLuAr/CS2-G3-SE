# Pull Request 工作流示例

Pull Request（PR，合并请求）从个人功能分支提交到 `dev`。在仓库根目录完成相关验证，再推送功能分支并创建 PR；具体命令见[小组协作规范](../README.md#小组协作规范)。本文给出描述模板与参考案例。

## PR 描述模板

创建 PR 时，建议使用以下结构：

```markdown
## 概述

这个 PR 做了什么、为什么做（一两句话）。

## 变更内容

- 按文件 / 模块列出改了什么
- 关键设计点、对外接口的变化（如果有的话）

## 自查清单

- [ ] 已运行代码审计（参考 `.agents/skills/code-review/SKILL.md`）
- [ ] 已运行相关测试（或说明为什么没有测试）
- [ ] 文档与实际代码一致（改了行为就同步改文档）
```

## 代码审阅时看什么

参考代码审计 skill（`.agents/skills/code-review/SKILL.md`）的检查清单：

### 核心检查维度

- **业务逻辑**：返回类型规范、异常使用、事务管理、业务规则完整性
- **安全性**：输入验证、SQL 注入防护、密码处理、权限检查
- **代码质量**：命名规范、职责单一、复杂度控制、错误处理
- **设计优雅度**（新增功能/重构时）：抽象是否恰当、继承是否合理、有没有更简单实现
- **文档同步**：系统总览、对应的前后端架构分册、README、功能清单和报告素材是否对应最终改动

### 具体检查要点

- **能不能跑**：导入路径、命名冲突、明显笔误
- **位置对不对**：改动是否落在约定的模块位置，接口是否与文档一致
- **分层合同**：用例层（Logic）创建并关闭数据库会话，统一提交或回滚；领域服务（Service）在传入会话中校验权限与业务；仓储（Repository）执行 SQL。浏览器页面通过 HTTP API 调用用例。
- **边界条件**：非法输入、失败路径会不会留下副作用（改了一半才抛异常）
- **测试**：新行为有没有对应的测试覆盖

> 审阅时指出具体问题、原因和建议，帮助队友一起完善实现。
> PR 与审阅记录会留档在 GitHub 上，最终报告里可以用它们说明团队协作与质量保证过程。

接口与事务依据见[后端架构](./architecture/backend.md)，页面、缓存和错误恢复依据见[前端架构](./architecture/frontend.md)。PR 中分别列出模拟测试、真实数据库测试和浏览器测试的实际结果，待验证的检查注明所需环境。
