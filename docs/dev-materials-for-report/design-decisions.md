### [2026-10-20] 补齐跨领域协作、编号传输和独立 CLI 任务路径

- **背景**：完整分层审计发现递补需要创建预约、写通知，共享事务的内部接口尚缺；消课结果需要保存实际操作者。浏览器使用 `number` 无法精确表达数据库允许的全部 BIGINT。CLI 独立运行时，进程内推荐快照和持久候补恢复也需要任务执行路径。
- **选项**：让 Logic 直接写各表，或通过明确的内部领域接口协作；HTTP 编号限制为 JavaScript 安全整数，或用字符串保留数据库范围；仅 Web 启动 Worker，或 CLI 与 Web 分别在本进程运行任务。
- **决定**：Logic 持有共享 Session 和统一 UTC 操作时刻，领域服务提供内部递补、关闭预约和通知生成合同；新增唯一消课记录表。Python/SQL 保持整数，HTTP/TypeScript 使用规范正十进制字符串。CLI 和 Web 默认启动单个 Worker，进程间候补处理由数据库锁协调，本进程推荐查询与刷新共用快照存储。
- **理由**：领域规则保留在服务中，预约、占用、候补和通知可以一起成功或回滚；消课可按预约核实原结果；字符串保留全部 BIGINT 精度；独立 CLI 有明确的推荐刷新与中断恢复路径。
- **影响**：同步后端合同、SQL、模型、Service、Repository、App、Web 类型、前端身份与错误类型及测试。推荐每 30 秒检查刷新请求或 10 分钟期限，刷新失败保留最近成功快照。候补历史重入和空位公平性继续保留待确认。

### [2026-10-19] 周期任务使用单线程顺序调度

- **背景**：候补核对与推荐刷新需要在 API 进程生命周期内周期触发，并在关闭时等待当前数据库用例完成。
- **选项**：为各任务分别创建线程；或者由一个 Worker 线程按到期时间顺序调用系统 Logic 入口。
- **决定**：使用单个后台线程顺序执行周期任务，隔离单个任务异常，并在停止时等待当前回调结束。
- **理由**：任务共享 App 装配的会话工厂，顺序执行可避免线程数量随任务增加，并让关闭顺序保持明确。
- **影响**：`App.start(with_worker=True)` 装配候补与推荐任务；默认 CLI 不启动 Worker。两个系统 Logic 入口仍为占位，业务调度尚未完成。

### [2026-10-16] 候补递补采用两事务 + reconcile，舍零窗口换系统简洁

- **背景**：候补递补涉及跨会员加锁（需要第二位会员的 member 行），与全局锁序（members 排最前）逆序。设计候补机制时需决定是否在 cancel 事务内同步递补，或分成两个事务。
- **三选二取舍**：以下三条性质无法同时满足：
  1. book 对候补无知（book 只认满员，不读队列）
  2. 取消与递补分成两个事务（锁序干净，不需跨会员加锁/有界重开）
  3. 零窗口（座位空出的瞬间，外人绝无可能抢在队首前）
  - 要 ①+③ → cancel 和 promote_next 必须同事务，引入有界重开的复杂度
  - 要 ②+③ → book 必须读队列让位，违反 ①
  - **本设计取 ①+②，舍 ③**
- **决定**：
  - `cancel` 提交后尽力同步调一次 `promote_next(session)`（在同请求内，近实时递补）。
  - `promote_next` 独立事务，按全局序先锁会员（无逆序），锁内复核队首是否仍 waiting 及资格，全过则建预约+通知，不过则关停该候补顺延。
  - Worker 每 5 分钟 reconcile 一遍「有空位+有waiting」的课次，补做 promote_next（崩溃恢复）。
  - `book` 合同不改，满员即拒。候补队列内部化，会员只能操作本人记录。
- **理由**：
  - 私教课容量 1，每次递补 0 或 1 人；FIFO 是尾部追加，队首只因离队变，新人插不进前面，所以天然不逆序。
  - 同步 promote 把窗口压到亚毫秒；私教课规模小，现实几乎不触发。即便触发也只是公平性小瑕疵（队首没递补，继续排下一轮空位），不是数据错乱。
  - 换来 book 彻底干净、锁序干净、队列完全内部化，系统更容易理解和维护；不需要有界重开、不需要破坏 book 合同。
- **影响**：
  - 三个地方共用统一冲突谓词（「有无与目标时段重叠的已确认预约」）：book/join_waitlist 检查抛 ScheduleConflict，promote_next 检查则关停并顺延。
  - `cancel` 返回值不改，仍返回 BookingView；前台想知道「递补给了谁」由 handler 在 cancel 后另查组合展示。
  - 递补产生的 booking 不写 operation_records（系统副作用，幂等由容量校验+状态转移保证）。
  - 待讨论点从 5 条收敛到 2 条（通知清理策略、通知记录内容设计）。

### [2026-09-28] 删除 v2 已替换的遗留表，实现干净 v3

- **背景**：把代码对齐 v3 时发现，001 迁移里仍保留 `card_products`、`memberships`、`consumptions` 三张 v2 表；它们对应的 `CardProduct`/`Membership`/`Consumption` 模型引用的 `CardKind`/`CardStatus` 已被删除，import 直接崩溃。而契约测试要求"每张 SQL 表都有对应模型"，必须决定这些表的去留。
- **选项**：
  1. **保留为 v2 遗留**：把模型里的 `CardKind`/`CardStatus` 字段降级为 `str` 修复崩溃，v2/v3 表在迁移期共存（符合"001 是 v2 基线、迁移到 v3"的叙事，改动小、风险低）。
  2. **删除已替换的遗留表**：v3 已用 `gym_card_products`+`lesson_package_products` 替代 `card_products`、用 `gym_cards`+`lesson_packages` 替代 `memberships`，直接删表和对应模型（最忠实 v3，但要处理 001 里指向它们的外键）。
- **决定**：选方案 2。删除 `card_products`、`memberships`、`consumptions` 及其模型；同时删掉 001 里被 003 重定义覆盖的死代码版 `payments`/`gym_entries`。保留 `accounts`、`bookings`、`course_sessions`、`equipment`、`maintenance_records`、`body_measurements`、`reviews`——这些 v3 仍在用，只是架构文档第 6 章未画出建表 SQL。
- **理由**：这是全新骨架、无历史数据要迁移，没必要背 v2 表的包袱；干净 v3 让后续实现者不会对着两套并存的产品/会员卡表困惑。判断"哪些是已替换、哪些仍需要"依据的是 v3 服务是否仍引用（如 `BookingService` 仍需 bookings）。
- **影响**：`001_initial_schema.sql` 删除 5 张表；`membership.py` 只保留 `GymEntry`；`booking.py` 删除 `Consumption`。契约测试的表覆盖检查转为纯 v3 表集合。

### [2026-09-20] 首版边界情况与问题讨论归档

**讨论来源与目的**：本记录整理项目发起人在本次设计协作中转述的小组回答、后续澄清及最终确认。目的是在实现前发现规则冲突和数据格式缺口，避免各模块分别猜测；不作为另一次组会或导师会议记录。当前有效接口和 SQL 以 [architecture.md](../architecture.md) 为准，下方更早的条目保留当时方案及其演变。

**讨论结论**：本轮首版业务边界已明确，未发现还需项目发起人决策的业务阻塞项。以下按“问题—决定—影响”保留报告可用的过程素材。

1. **门禁次数是否就是私教节数？** 两者原先都称为“次数”，容易在预约、签到和入场时混扣。最终分开：月/季/年门禁为 30/90/365 天，赠课为 20/64/256 节；次卡无期限，含 10 次入场、不赠课，也不能约私教。赠课曾按 30/90/365 节讨论，后由发起人调整为低于有效天数的配额；每天能入场不代表每天都有一节可用私教。字段和 SQL 分别约束入场余额与私教余额。
2. **卡在预约当天有效，是否就能预约任意未来课程？旧赠课能否配新卡？** 最终按上课开始日期校验同一张来源卡；旧卡到期后赠课失效，不能组合新旧卡或转移余额。例如旧卡 9 月 30 日最后有效，不能用它约 10 月 1 日的课。账面余额保留作历史，不当作可用权益；已合法预约的到期前课程仍能事后补签和结算。
3. **月卡按自然月还是固定天数？过期日最后一分钟怎样处理？** 固定 30/90/365 天，生效日算第 1 天；最后有效日的整个 23:59 分钟均有效，次日 00:00 失效。数据库保存“最后有效日的次日”，统一使用前含后不含的日期判断，避免月份长度、闰年和小数秒产生不同解释。
4. **提前续购会浪费重叠天数吗？** 新期限卡自动接在全部未作废期限卡的末尾，未来卡也计入；没有未到期卡则当天生效。次卡当天生效且不参与接续，不开放手选日期。旧卡最后有效日 9 月 30 日，新月卡从 10 月 1 日起至 10 月 30 日；可以提前约新卡有效期内的课。SaleInput 删除手选日期，日期在会员锁内计算，防止同时购卡产生重叠。
5. **重复入场、换卡或重试会不会多扣次？** 同一会员同一门店日期只扣一次。上午用掉次卡最后一次，晚上仍可入场；换用自己的另一张卡也不再扣。入场记录使用“会员＋日期”唯一约束，扣次与记录一起提交；相同请求跨午夜重试仍指向原记录，下一天的真实入场用新编号。门禁登记不由课程签到代替。
6. **课程时长、取消时间和补签窗口是否是一回事？** 每节私教最长 150 分钟，不额外规定营业时段；取消必须在开课前，恰好开课时已不能取消。开课起至结算前可签到、更正，教练可在下课后替补签。CLI 通过选择课次和到场状态操作，无需先实现扫码；补签记实际操作时间，不伪造课内时间。
7. **缺席是否扣课，结算后改签到会影响什么？** 预约先占用 1 节；取消或缺席只释放占用，消课才扣 1 节。已记缺席后补签可能遇到释放的节数已被别课占用，已消课后改缺席又涉及退节数与历史记录。首版因此只允许结算前更正，消课/缺席操作先提示确认，结算后不开放直接修改或冲正。
8. **教练曾经教过会员，就能永久查看所有新体测吗？** 历史查看权永久保留，但没有有效预约后停止更新，再次预约本教练后恢复最新历史。例如最后一课 9 月 20 日结束，9 月 21 日新录入记录暂不可见，再次有效预约后可见。范围按实际录入时间 created_at 判断，不按可补填的测量时间 measured_at；详情、列表总数及对比统一过滤，补签不延长权限。身高固定 100–250 cm、体重 30–150 kg，均含边界。
9. **规则明确后，是否就能声称实现完成？** 不能。列表统一 Page、详情统一 View、失败抛异常，改字段同时改 SQL、签名和调用说明；这些是实现约定。静态一致性和 SQL 逻辑样例只能检查部分设计，不能证明真实数据库事务、并发和交互正确。

**剩余事项的归属**：密码哈希库、数据库访问工具、测试工具及依赖版本由对应实现负责人验证后确定；可选 TUI 随进度安排。冻结、退款、候补和结算后冲正不进入首版。这些不作为本轮卡、预约、签到和体测规则尚未决定的理由。

**转为验收材料**：正常、刚好到边界、越界、重复请求和权限拒绝等用例由对应模块负责人在实现时补齐。已做检查及其限制见[测试笔记](./testing-notes.md)；尚未执行的业务场景不能写成测试通过。功能清单中首版 84 项统一标为“待开发”，4 项 P2 候选保留“待确认”；这表示首版需求已明确，不表示实现或验收完成。

### [2026-09-20] 数据格式定型、骨架搭建与接口复核

**背景**：项目发起人要求先固定数据格式和接口签名，避免上学期返回类型反复变化的问题；在实现业务逻辑前建立完整骨架，明确模块边界。

**数据格式约定**：
- 列表统一返回 `Page[T]`，详情返回 `*View`，失败抛异常，不混用字典、列表或 None
- 金额用 `Decimal` 两位小数，时间带时区转 UTC，ID 用正整数，状态用 `Literal` 固定值
- `*Input` 提交全部可编辑字段，`*View` 是脱离数据库会话的普通对象
- 接口变更必须同步调用方、测试和文档

**骨架与占位**：
- 按已确认分层建立 `src/` 各层包、`tests/` 分类目录、`sql/` 脚本位置
- 类、字段和方法签名按设计补齐，方法体统一抛 `NotImplementedError` 表示未实现
- SQLAlchemy 仅类型检查时导入，骨架不连接数据库；CLI 不依赖可选 TUI 库

**接口复核与修正**：
- 分页保留请求参数；`CardQuery` 增加 `valid_on` 字段；档案移交明确目标账号
- 课次保存课程名称/类型快照；增加排课/预约的请求结果查询接口
- 提交未知异常携带原请求/记录编号；操作名使用固定 `Literal`
- 门店日期相关的服务和交互入口显式接收时区；未绑定档案的 None 不混淆为"不限制查询"

**业务细则确认**：
- **预约用卡**：上课日期必须在所选卡有效期内，采用门店日期与前含后不含格式
- **密码输入**：允许 ASCII 字母、数字、短横线、下划线，长度 1-32 位，不做大小写转换，保存哈希
- **权限角色**：现有四类角色（会员、教练、前台、管理员）与数据归属检查继续作为当前设计
- **当时待确认项**：卡适用范围、有效期计算、取消签到窗口、缺席扣次、体测合理范围；这些问题后来已逐项明确，见本页上方的讨论归档与当前架构设计。

**协作边界**：
- 办卡与收款由不同人负责但共用一次事务；签到与消课共用 `AttendanceService`
- 共同负责的功能在 CSV 开发备注中写明本次修改范围
- 异常处理统一在 `src/errors/` 定义和处理，事务清理由业务服务负责

**影响**：架构和接口定型后，实现功能时直接补对应方法体；返回类型变化仍须同步设计、调用方与测试。建好骨架不等于业务已实现，功能进度以实际代码和验收为准。
