# 项目规范

这份文档约定大家怎么写、怎么检查、什么时候算完成。Git 操作教程见 [README](../README.md#小组协作规范)。

## 文档与说明要求

文档、注释和协作说明应交代必要前提、具体步骤与预期结果，方便按任务查阅；不评价成员的经验或技术水平。

- 解释和注释优先用中文；文件名、类名、参数、命令保留准确英文，首次出现配中文含义。例如 `MemberService` 是“会员业务服务”，不要只写“调 service”。
- 写操作指引时说明：开始前需要什么、在哪个目录操作、步骤是什么、成功时能看到什么、失败后如何排查。占位符要说明如何替换。
- 先用一个具体例子解释目的，再介绍术语。不要把“配置好环境”“补一下测试”“按架构实现”当作完整指引。
- 区分当前可执行的命令与计划中的示例；未创建的文件明确标注，未运行过的测试不能写成通过。
- 方法说明写清输入、返回结果、可能的错误和会修改的数据；用中文解释特殊规则，不要求给每一行简单代码加注释。
- 阅读与任务步骤统一维护在[文档索引](./README.md#从这里开始)，避免每份文档各写一套不同流程。

## 代码约定

- 文件、函数、变量用 `snake_case`，类用 `PascalCase`，常量用 `UPPER_SNAKE_CASE`，即 PEP-8 风格。
- 使用 UTF-8、4 空格缩进；公开方法补参数和返回值的类型注解。
- 实现前先对齐[数据格式](./architecture.md#字段类型规则)、Python 类型与 SQL 字段。业务列表始终返回 `Page[T]`（空结果的 items 为空列表），详情返回对应 View，失败抛异常；禁止同一函数在字典、列表、None 之间切换。
- 接口改动须同时修改类型定义、实现、调用方、文档和相关测试，并让对接组员复核。查询测试覆盖零条、一条、多条、记录不存在和无权限，检查返回结构和异常类型。
- 一个函数尽量只做一件事；复杂规则写明原因，避免只复述代码的注释。
- CLI / TUI 负责输入和展示，共用服务负责业务规则，数据库模块负责读写；不要在交互处理里直接写 SQL 或扣次数。
- CLI 内部区分交互循环、菜单、操作处理器、输入和格式化；操作处理器按业务模块拆分。输入格式检查与服务层业务校验各负其责，结构见[框架方案](./architecture.md)。
- 复用已有的配置、日志、数据库和校验方法；新增依赖先说明用途。
- 数据库地址、密码等从环境配置读取，不提交 `.env`、真实数据、日志和虚拟环境。

## 配置、异常与日志

- 部署参数集中配置；业务阈值只定义一次；模块私有常量留在使用它的文件。卡价等业务数据放数据库。
- 错误输入、余额不足、预约满员等给出清楚的中文提示；不要用 `except: pass` 吞掉错误。
- 业务异常统一定义在 `src/errors/`；服务回滚后抛出，由统一错误处理入口生成提示并按需记录日志，最后交给 CLI/TUI 展示。错误处理入口不接管业务事务，详见[账号与日志模块](./architecture.md#账号与日志模块)。
- 日志记录操作、时间、相关记录 ID 和失败原因，不记录密码、完整联系方式或体测明细。
- 数据库查询使用参数化语句；金额用 `Decimal` / `DECIMAL`，避免浮点误差。

## 质量要求

- CLI 能独立走通主流程：建档办卡 → 约课 → 签到 → 消课 → 评价 → 查看报表；TUI 是可选增强，不作为核心功能完成的前提。
- 默认启动不能依赖 TUI 库；`--tui` 未就绪时有明确提示，已实现时验证两种入口使用相同的业务规则。
- 非法输入、空列表、记录不存在、重复操作不会让程序无故崩溃。
- 办卡与收款、预约与额度占用、消课与扣次应在同一数据库事务中完成，失败不能只改一半。
- 权限在服务层检查：会员只能操作自己的数据，教练只能管理自己负责的课程；不能只靠隐藏菜单。
- 新增业务与修复 bug 要验证正常、边界和失败情况；关键事务需用真实 MySQL 检查回滚、重复请求与并发冲突。
- 测试检查最终结果，例如余额、预约状态和数据库记录，而不只是“某个函数被调用”。

## 协作与完成标准

1. 开始前在[功能清单](./feature-list.csv)查自己的暂定任务，确认相关模块接口；共同负责的条目先约定本次修改范围，避免重复实现。
2. 日常在 `dev` 或个人功能分支开发；跨模块、数据库结构和重要业务规则变更通过 PR 让另一位组员复核。
3. 完成后运行相关测试，同步文档与 CSV。只有入口或空类不算功能完成。
4. “已完成”意味着功能可操作、验收要点满足、相关测试通过；在开发备注里留下实现或 PR、测试说明。
5. 设计决定、遇到的问题、组会结论随手记入现有的[报告素材目录](./dev-materials-for-report/)，不补写虚构的过程。

文档先写当前需要的内容。尚未决定的标“待定”，尚未实现的标“计划”，后续按实际开发补充字段与接口。当前架构已由项目发起人确认；按已确认范围推进，不因原来的审批约定重复等待。业务细则和具体依赖版本仍须明确区分是否已确定。
